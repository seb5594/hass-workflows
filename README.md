**One private engine for every Home Assistant project.** Public repositories keep one short caller workflow, their app/integration code and a handful of [managed files](#managed-files) GitHub insists on reading locally. Metadata from `config.yaml` or `manifest.json` determines the validation, build, badges, and release behavior.

| Building block | Purpose |
| --- | --- |
| [Project action](.actions/project/action.yml) | Single CI and publishing entry point; detects the project type |
| [App catalog](.actions/catalog/action.yml), [integration catalog](.actions/catalog-sync/action.yml), [hub](.actions/hub/action.yml) | Hourly sync of the app and integration [catalogs](docs/CATALOG.md) and the [hub](docs/HUB.md) |
| [Setup action](.actions/setup-python/action.yml) | Python plus the one pinned PyYAML every other action and the engine checks reuse |
| [Scripts](.scripts/) | All logic, see [Architecture](docs/ARCHITECTURE.md) |
| [Renovate preset](default.json) | Shared dependency rules, copied into every repository, see [Renovate](docs/RENOVATE.md) |
| [Templates](.templates/) | Caller workflows (one per family), the [snippets](.templates/snippets/) they share, README texts and the other [managed files](#managed-files) |

## Conventions for projects

Related apps may share one release by declaring an ordered, exhaustive list in
`.github/apps.json`, for example `{"apps": ["untuyaos3", "untuyaos3_wifi"]}`. Every
listed app must have the same version and repository URL, and no detected app may
be omitted. The first app supplies the README header and release notes. The normal
project caller validates and builds every member, publishes each multi-architecture
image, and attaches all image references to one GitHub release. Repositories without
this file retain the single-app rule. Project checks in `.github/checks/` also run
for apps; companion image measurements cannot overwrite the primary app's badges.

| Path in the project | Meaning |
| --- | --- |
| `.github/workflows/ci.yml` | The caller. Must equal the template for the pinned engine commit; CI fails on drift |
| `.github/tests/` | All tests, kept out of the repository root (`tests/` is accepted as a fallback) |
| `.github/ha_tests/` | Integrations only: tests against a real Home Assistant core. Never part of the regular run; the Compatibility workflow runs them for every Home Assistant release from the `hacs.json` minimum upwards (see below) |
| `.github/workflows/compat.yml` | The Compatibility caller of a project with `ha_tests`, kept in step like `ci.yml` |
| `custom_components/<domain>/brand/` | Integrations only: `icon.png` (256), `icon@2x.png` (512), `logo.png`, `logo@2x.png` and `dark_` variants. Keep the SVG sources in the project and render them with `node .engine/.scripts/render_brand.cjs <svg folder> custom_components/<domain>/brand`; the sizes are checked on every build |
| `.github/checks/*.py` | Optional project-specific rules, executed from the repository root |
| `.github/dev/requirements-dev.txt` | If present (the root works too), installed before the integration tests, which then run with pytest |
| `[tool.pycodestyle]` in `.github/dev/pyproject.toml` | Opts an integration into the style check; pytest settings go in the same file |
| README header | Display name, logo, separator and badges, generated by [`readme.py`](.scripts/readme.py) from the metadata; everything below it is yours |
| `.github/metrics.json` | Written by the pipeline: the last measured test count, sizes and pulls behind the README badges |
| `LICENSE` (or `LICENSE.md`, `LICENCE`) | Named and linked in the generated License section at the end of the README |

### Integration consistency checks

Every integration build runs [`integration_checks.py`](.scripts/integration_checks.py) before the project's own checks. It fails on a `translations/en.json` that differs from `strings.json`, on a translation with keys English lacks the other way round (a missing key fails, an extra key only warns), on services or fields that exist in `services.yaml` but not in the English texts (or the reverse) or lack a name or description, on a ZIP release whose `filename` is not `<domain>.zip`, and on brand images with the wrong size. Rules that belong to one project stay in its `.github/checks/`.

### Managed files

GitHub only reads workflows, Dependabot, Renovate and funding settings from the repository itself, so they cannot be shared by reference. [`managed.py`](.scripts/managed.py) renders them from one template each, and CI fails when a copy drifts:

| File | Template |
| --- | --- |
| `.github/workflows/ci.yml`, `update.yml` | [`.templates/callers`](.templates/callers/), built from [snippets](.templates/snippets/) (`# include: NAME`) for the steps several workflows share |
| `.github/workflows/compat.yml` | Integrations with `.github/ha_tests` only |
| `.github/dependabot.yml` | [`.templates`](.templates/) |
| `.github/renovate.json` | The whole [`default.json`](default.json), see [Renovate](docs/RENOVATE.md) |
| `.github/FUNDING.yml` | Built from the donation links in [`config.py`](.scripts/config.py), the same ones the README badges use |
| `<app>/entrypoint.sh` | Shared startup code of apps that do not run on s6 |
| `.github/DEVELOPMENT.md` | Catalogs only: how the generated catalog is maintained |

`python .engine/.scripts/managed.py sync <kind> <engine-sha>` inside a repository rewrites all of them (`kind`: `app`, `integration`, `catalog-apps`, `catalog-integrations` or `hub`); `check <kind>` is what CI runs. Public apps, integrations and the integration catalog share the **Home Assistant CI** name.
The read-only compatibility workflow resolves stable and preview releases daily.
The integration catalog keeps its release ZIP and feed semantics and its historical
tests on external pull requests. Project-specific firmware, camera, router and
store-promotion tests stay alongside the code that they exercise.

Changing a template and re-running `sync` in every repository is the whole update procedure.

## Home Assistant compatibility

An integration that keeps the lowest possible Home Assistant version proves it. [`ha_matrix.py`](.scripts/ha_matrix.py) builds one environment per release in [`ha_releases.json`](.scripts/ha_releases.json) (the release, its matching [pytest-homeassistant-custom-component](https://github.com/MatthewFlamm/pytest-homeassistant-custom-component) and Python) and runs two suites in it: the regular `.github/tests` and the real-core `.github/ha_tests`. The shared pytest plugin [`hass_real_tests.py`](.scripts/hass_real_tests.py) boots the core, makes `custom_components` discoverable and treats the manifest dependencies as loaded, so a project only adds its own doubles.

The Compatibility workflow lists the releases at or above the minimum in `hacs.json` and tests each in its own job, daily and for relevant project changes. Each live run also resolves the current stable and preview versions from PyPI. See [compatibility testing](docs/COMPATIBILITY.md) for fixture selection and the frozen CI targets. Locally: `python .engine/.scripts/ha_matrix.py run 2026.9.4`; `list` prints the releases as JSON. A release is added to the table together with the first test run that proves it works.

## Release flow

Apps use static versions throughout: a tagged base image and exact `apk` package versions, enforced during validation. They build each declared platform, run shell/YAML/Docker lint and the available runtime tests, then publish into one stable GHCR package per app, `ghcr.io/seb5594/hass-APP`. The tag follows `ARCH-hass-APP-vVERSION`, for example `amd64-hass-git-exporter-v1.18.1`. The multi-platform manifest drops the architecture: `hass-git-exporter-v1.18.1`, also tagged `latest`. Each version gets a GitHub release with per-architecture image references. Users can still build locally until prebuilt images are selected in the app configuration.

Apps can opt into calendar versions: `YYYY-MM-DD` for the first build of a Europe/Berlin day,
then `.2`, `.3`, and so on. The version bumper preserves this format, starts a fresh date on a
later day and never moves backwards. The dotted spelling `YYYY.MM.DD.BUILD` numbers every build,
starting at `.1` each day (`2026.11.10.1`, `2026.11.10.2`, then `2026.11.11.1`); it reads the same
in an app's `config.yaml` and an integration's `manifest.json`. Date separators do not mark a pre-release. Existing
numeric and pre-release version formats keep their behavior; `stage: experimental` remains
an app metadata choice.

The current Home Assistant base image ships amd64 and aarch64 only. An app that lists armv7, armhf or i386 as well builds those on the previous generation of base images (`ghcr.io/home-assistant/ARCH-base:3.22-2025.11.1`, see [`legacy.py`](.scripts/legacy.py)), whose Alpine is older. Each apk pin is therefore a build argument with a legacy twin (`ARG GIT_VERSION=2.54.0-r0` next to `ARG GIT_VERSION_LEGACY=2.49.1-r0`); the build hands the legacy value to the Dockerfile on those architectures, and validation insists on a twin for every pinned package. Only these prebuilt images exist for them: a local build by the Supervisor does not know the twins.

Integrations run the HACS checks (skipped for private and template repositories, which HACS cannot read; the `brands` and `topics` checks only the default store needs are always skipped, and so is `license` while the repository has no license file, which a warning points out), Python lint and tests (pytest when `requirements-dev.txt` exists, otherwise unittest, plus `*.test.cjs` frontend tests through Node). Every CI run produces a verified ZIP artifact. A new manifest version publishes the ZIP as a GitHub release whose notes end with the ZIP's SHA-256 (there is no checksum file); versions such as `1.0.0b1` become pre-releases (see `zip_release` below).

The README install badge reads *HACS · Marketplace*. From Home Assistant 2026.11 HACS is built in as the Marketplace, which reads the same `hacs.json` and catalog. The badge keeps the `hacs_repository` My link on purpose: the Marketplace accepts it with identical parameters, whereas the newer `marketplace_repository` link does not exist on older instances. The `hacs/action` checks stay as they are.

`zip_release` in `hacs.json` is optional. HACS installs a ZIP release from the newest *stable* release only, and it only counts downloads of the asset it installs. A repository whose releases are all pre-releases would fail to install with it (HACS falls back to the branch and asks for a release URL that does not exist). So while a project with `zip_release` has not released a stable version yet, its newest beta is published as a regular release, and an existing beta release is corrected the same way on the next run. Once a stable version exists, betas carry the pre-release marker again and HACS offers them behind its beta switch. Without `zip_release` HACS copies the component folder from the repository and the ZIP serves manual installs only.

Integration tag prefixes can be overridden per repository in `INTEGRATION_TAG_PREFIXES` in `.scripts/config.py`. DeepL Translator uses the version without a leading `v` for both its tag and stable release title; its generated caller accepts numeric tags. Other repositories keep their existing format.

A release is titled by its version only (`v1.2.0`, without the project name). A pre-release carries just its stage as the title, `Beta 3` for `1.0.0b3` or `1.0.0-beta.3`: the numeric part only keeps the git tag a proper version.

The build and smoke-test phase executes once per architecture. Publishing pushes the tested images instead of rebuilding them. A version already released on `main` remains unchanged; a matching `vVERSION` tag can republish app images deliberately. Starting the workflow by hand offers a `draft` switch that keeps the release private for review.

## README header

Every README starts with a generated header, centered: the display name, the logo (`logo.png`, otherwise `icon.png`; nothing if there is neither), a separator and the badge rows. Integrations take the pictures from `brand/` of the component, apps from their folder; `@2x` and `dark_` variants are picked up. The text below the header is yours; the pipeline never touches it. READMEs written before the header existed are converted on the next refresh (old title, logo and badge block are replaced).

The badge rows come in three sizes, set by the `HERO`, `MAJOR` and `MINOR` tiers in [`badgekit.py`](.scripts/badgekit.py):

| Row | Size | Integration | App |
| --- | --- | --- | --- |
| 1 | 1.4x | HACS install, minimum Home Assistant, newest release | install, minimum Home Assistant, newest release, GHCR pulls |
| 2 | normal | stars (when above zero), downloads of the newest release, open issues, tests (when measured), checks, license (when present) | architectures, stage, ingress, mounts, privileges, image size |
| 3 | normal | | the facts of row 2 of the integration, with runtime tests |
| last | 2x | Support PayPal, Support Buy Me a Coffee | the same |

The rows share one centered paragraph, separated by line breaks, so they stay close together.

Which badge sits in which row is decided in one place: `INTEGRATION_LAYOUT` and `APP_LAYOUT`. Editing a list there changes every project README and catalog entry. Conditional badges appear only when they have something to show, and a README cannot hide badges by itself, so the pipeline asks GitHub for the current values and rewrites the header on every run from the default branch (and weekly via the schedule trigger); CI only checks that the generated block exists. The version badge shows the newest published release (the metadata version before the first one); the downloads badge counts that release's assets and appears once a release exists, even at zero. The minimum Home Assistant badge links to the Compatibility workflow when the project has one. Catalogs and the hub reuse the layout per project without the donation, install and license badges.

Every README also ends with two generated sections: "Say thanks" with the donation links in the larger `for-the-badge` style (text: `SUPPORT_TEXT` in `badgekit.py`), and "License" as the very last one. The license section names the license found in the repository's license file and links it ([`licenses.py`](.scripts/licenses.py)); without a license file there is none. Text added below these sections is moved above them on the next refresh.

Measurements come from the pipeline itself and are kept in the project's `.github/metrics.json`, committed together with the README:

| Measurement | Source |
| --- | --- |
| Image size per architecture, runtime tests | App build and smoke tests |
| Image pulls | Public GHCR package page (kept unchanged if the page cannot be read) |
| Test count, ZIP size | Integration tests and packaging |

They are rendered as ordinary static badges, so nothing depends on a separate branch or a Shields endpoint. A value is only rewritten when the badge would show something different (sizes to 0.1 MiB, pulls as 1.2k), which keeps the refresh commits rare. Catalogs read the same file of every project they list.

## Public caller contract

### Apps that use upstream image versions

An app can opt in with `.github/upstream.json`:

```json
{"versionArgument": "GITEA_MIRROR_VERSION", "majorUpdates": "approval"}
```

The selected annotated Dockerfile ARG supplies the exact app version (without `v`). CI checks
that `config.yaml`, `BUILD_VERSION`, and the primary image agree. The daily follower considers
only releases within the current major. Managed Renovate configuration requires Dependency
Dashboard approval and disables automerge for major Docker updates, including runtime images.
Approval creates a PR; the maintainer reviews breaking changes and merges it manually.
Base-image and package-only changes retain the upstream version and ship with its next release.
Projects without this opt-in retain the existing version-counter behavior.

### Engine access

The public workflow checks out this private repository at a reviewed commit through `ORCHESTRATION_PAT`. GitHub's Actions sharing switch does not grant `actions/checkout` access to a private secondary repository from a public caller. The token must select `hass-workflows` with **Contents: Read**. App catalog notifications also need **Contents: Read and write** for `Home-Assistant-Apps`, and the catalog repository itself needs the same secret to fetch this engine. The source repository's `GITHUB_TOKEN` publishes its own release and images and commits the README refresh.

Fork pull requests cannot access the private engine and are skipped. The central [engine validation](.github/workflows/engine-validation.yml) runs the unit tests and then every repository listed in `PROJECTS` in [`config.py`](.scripts/config.py) (apps, integrations and the template) without publishing. It runs the callers' `main` branches, so it passes once their README and workflow changes are merged.

## Honest project metrics

Badges only show what can be measured. GitHub release badges count release assets, which is meaningful for integration ZIPs but not for apps, whose releases carry small image references; apps therefore show GHCR pulls instead. Local Home Assistant builds and installations are not counted anywhere. GitHub does not expose download country or continent data, so none is shown.

App repositories may declare `.github/images.json` as a map from installed app slug to a GHCR package name (for example `{"tuya_breaker":"hass-tuya-breaker"}`). This lets a standalone repository publish to its own fresh package after a split while preserving its Home Assistant slug. The owner always remains the workflow repository owner; existing projects without this file retain their registry names. Published release tags/assets are never rewritten by an ordinary source-branch run.

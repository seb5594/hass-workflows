**One private engine for every Home Assistant project.** Public repositories keep one short caller workflow, their app/integration code, and the `.github/dependabot.yml` file GitHub requires locally. Metadata from `config.yaml` or `manifest.json` determines the validation, build, badges, and release behavior.

| Building block | Purpose |
| --- | --- |
| [Project action](.actions/project/action.yml) | Single CI and publishing entry point; detects the project type |
| [Catalog action](.actions/catalog/action.yml) | Hourly sync of the app and integration [catalogs](docs/CATALOG.md) |
| [Hub action](.actions/hub/action.yml) | Front page that merges both catalogs, see [Hub](docs/HUB.md) |
| [Scripts](.scripts/) | Validation, builds, releases, README badges, metrics and catalog logic |
| [Renovate preset](default.json) | Shared dependency rules, see [Renovate preparation](docs/RENOVATE.md) |
| [Caller templates](.templates/) | Workflows copied into projects, plus catalog text, Dependabot config and entrypoint |

## Conventions for projects

| Path in the project | Meaning |
| --- | --- |
| `.github/workflows/ci.yml` | The caller. Must equal the template for the pinned engine commit; CI fails on drift |
| `.github/tests/` | All tests, kept out of the repository root (`tests/` is accepted as a fallback) |
| `.github/checks/*.py` | Optional project-specific rules, executed from the repository root |
| `requirements-dev.txt` | If present, installed before the integration tests, which then run with pytest |
| `[tool.pycodestyle]` in `pyproject.toml` | Opts an integration into the style check |
| `.github/renovate.json` | Optional; must equal the template, which extends the shared preset |
| README badge block | Generated by [`readme.py`](.scripts/readme.py); run it again after changing metadata |

To update a caller, copy [`ci.yml.tpl`](.templates/app/ci.yml.tpl) (apps) or [`ci.yml.tpl`](.templates/integration/ci.yml.tpl) (integrations) and replace `__ENGINE_SHA__` with the engine commit to use.

## Release flow

Apps use static versions throughout: a tagged base image and exact `apk` package versions, enforced during validation. They build each declared platform, run shell/YAML/Docker lint and the available runtime tests, then publish into one stable GHCR package per app, `ghcr.io/seb5594/hass-APP`. The tag follows `ARCH-hass-APP-vVERSION`, for example `amd64-hass-git-exporter-v1.18.1`. The multi-platform manifest drops the architecture: `hass-git-exporter-v1.18.1`, also tagged `latest`. Each version gets a GitHub release with per-architecture image references. Users can still build locally until prebuilt images are selected in the app configuration.

Integrations run HACS checks (skipped for private and template repositories, which HACS cannot read), Python lint and tests (pytest when `requirements-dev.txt` exists, otherwise unittest, plus `*.test.cjs` frontend tests through Node). Every CI run produces a verified ZIP artifact. A new manifest version publishes the ZIP and `SHA256SUMS.txt` as a GitHub release; versions such as `1.0.0b1` become pre-releases.

The build and smoke-test phase executes once per architecture. Publishing pushes the tested images instead of rebuilding them. A version already released on `main` remains unchanged; a matching `vVERSION` tag can republish app images deliberately. Starting the workflow by hand offers a `draft` switch that keeps the release private for review.

## README badges

The badge block of every project is generated from its metadata and arranged in tight rows: release, community, platform (architectures), access (mounts), capabilities, quality, install, and a last row with the donation links alone. Static rows come from `config.yaml`, `manifest.json` and `hacs.json`; live rows use the GitHub API.

Pipeline metrics are published after each release-eligible run to the project's `badges` branch as [Shields endpoint](https://shields.io/badges/endpoint-badge) files and referenced by the README:

| Metric | Source |
| --- | --- |
| Image size per architecture, runtime tests, build time | App build and smoke tests |
| Image pulls | Public GHCR package page (skipped if the page cannot be read) |
| Test count, HACS ZIP size | Integration tests and packaging |
| Last build | Publishing run |

The branch is replaced with a single commit on every run, so it adds no history. Until the first publishing run the metric badges show an error.

## Public caller contract

The public workflow checks out this private repository at a reviewed commit through `ORCHESTRATION_PAT`. GitHub's Actions sharing switch does not grant `actions/checkout` access to a private secondary repository from a public caller. The token must select `hass-workflows` with **Contents: Read**. App catalog notifications also need **Contents: Read and write** for `Home-Assistant-Apps`, and the catalog repository itself needs the same secret to fetch this engine. The source repository's `GITHUB_TOKEN` publishes its own release, images and badge branch.

Fork pull requests cannot access the private engine and are skipped. The central [engine validation](.github/workflows/engine-validation.yml) checks both apps and an integration without publishing. It runs the callers' `main` branches, so it passes once their README and workflow changes are merged.

Each project's `.github/dependabot.yml` stays in that project: GitHub reads it there and cannot consume a template from another repository. Its contents are checked against [the shared template](.templates/dependabot.yml).

## Honest project metrics

Badges only show what can be measured. GitHub release badges count release assets, which is meaningful for integration ZIPs but not for apps, whose releases carry small image references; apps therefore show GHCR pulls instead. Local Home Assistant builds and installations are not counted anywhere. GitHub does not expose download country or continent data, so none is shown.
